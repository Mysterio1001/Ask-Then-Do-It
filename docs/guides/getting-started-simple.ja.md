# Ask Then Do It：初心者向けフロー

Ask Then Do It には `Full` と `Lite` の 2 つのフローがあります。Full は完全な意思決定記録と高い検証信頼度が必要な作業向けです。Lite は範囲が明確でリスクが低く、フローに使う文章量を減らしたい作業向けです。

どちらのモードも、範囲を明確にし、利用者の許可を得て、既存の変更を保護し、検証結果を正直に報告してから完了を主張します。Lite は Full より簡潔ですが、リスク確認や検証を省略する許可ではありません。

## モードの優先順位

Codex は操作を始めるたびに、次の順序でモードを決定します。

1. 「今回は Full」「今回は Lite」など、現在の操作に対する明示的な指示。
2. プロジェクト Config。
3. ユーザー Config。
4. 有効な設定がない場合の Full fallback。

現在の操作に対する明示的な指示はその操作だけに影響し、Config には書き込みません。プロジェクト Config はそのプロジェクトだけに影響し、他のセッションでは引き続き Config が基準です。Config のパス、形式、エラー処理は [Codex Plugin 使用ガイド](codex.ja.md)を参照してください。

Generic workflow は Codex Config を読めません。代わりに貼り付けたワークフローの先頭付近にあるデフォルトモード宣言を使います。現在の操作への明示的な指示が優先され、宣言がないか無効な場合は Full を使います。詳しくは [Generic 使用ガイド](generic.ja.md)を参照してください。

## Full と Lite の比較

| 比較項目 | Full | Lite |
| --- | --- | --- |
| 適する作業 | 高リスク、複数モジュール、未確定の要件、または完全な監査経路が必要な作業 | 範囲が明確でリスクの低い変更 |
| 質問 | 要件の合意まで一度に一つ | 1 回につき最大 3 個、全体で約 500 tokens |
| フロー文書 | 要件、プロジェクト知識、仕様、Ticket 計画、実装根拠を保存 | Change Brief は会話内だけに表示し、フロー文書を作らない |
| 実装前の承認 | 要件、仕様、Ticket 計画の 3 点 | Change Brief の 1 点 |
| テスト | 各 Ticket でテストを追加するか利用者が決定 | テストを追加も変更もせず、TDD を行わない |
| 検証 | Ticket のモードとリスクに応じた完全で追跡可能な検証 | 静的チェックと、成功経路および失敗または境界経路を一つずつ |
| Review | 独立した 12 の視点と根拠 | 同じ AI の簡潔な Review。findings の修正前には利用者の承認が必要 |
| 追跡可能性 | 高く、保存した文書から別セッションで再開可能 | 低く、保存されていないフロー状態は新しいセッションへ引き継がない |

## Full モード

Full は要件の質問を一度に一つだけ行い、別のセッションでも確認できる文書を残します。Full には要件の合意、仕様、Ticket 計画という 3 つの正式な承認点があります。

1. **現状を理解する。** AI はプロジェクトの指示、関連するコード、テスト、設定、現在の変更を読み、無関係な作業には触れません。
2. **要件の合意を得る。** 推奨回答と主なトレードオフを添えて、要件の質問を一度に一つ行います。利用者の承認後にプロジェクト知識を更新でき、これが最初の承認点です。
3. **仕様を書く。** 仕様は本番コードを書かずに、観測可能な動作、失敗時の動作、境界を定義します。完全な仕様への承認が 2 番目の承認点です。
4. **縦割りの Tickets に分ける。** 各 Ticket は独立して検証できる結果を届けます。AI は Ticket ごとにテスト方針を提案し、テスト実行で時間が増える場合があること、追加しないと信頼度が下がることを説明します。その後、すべての Ticket についてテストを追加するかどうかを一度に回答し、完全な Ticket 計画を承認します。これが 3 番目の承認点です。
5. **テスト選択に従って実装する。** Full の内部では、テストを追加する選択と追加しない選択が `tdd` と `direct` に対応します。利用者がこれらの内部名で回答する必要はありません。
6. **実装根拠を残す。** `$implement-tdd` は実際の `Red`、`Green`、`Refactor` の結果を記録します。`$implement-direct` は振る舞いテストを作成も実行もしませんが、lint、型チェック、build は実行でき、`tests: skipped-by-user` と未テスト範囲を記録します。
7. **Review する。** Review は承認済み内容、差分、検証結果を 12 の視点で比較します。システム全体の問題はアーキテクチャ改善として分析し、変更範囲を黙って広げず仕様と Ticket 計画へ戻します。
8. **完了する。** AI は提供した動作、観測した検証、得られなかった根拠、残存リスクを報告します。保存した文書から後のセッションで続行できます。

無回答、無関係な返答、AI 自身による状態変更は、いずれの承認の代わりにもなりません。

## Lite モード

Lite は範囲の定まった変更を少ないフロー文章で進めます。1 回につき最大 3 個の阻害質問だけを行い、実装を妨げるか方向を大きく変える決定だけを確認します。

1. **現状とリスクを理解する。** AI は現在の操作に関係する指示、変更、コード、テスト、設定、文書だけを確認し、作業案を出す前に重大なリスクを評価します。
2. **阻害要因だけを質問する。** 1 回につき最大 3 個の阻害質問を影響と不確実性の順に並べます。各質問は 3 つ以内の短い文で一つの決定だけを尋ね、推奨案と主なトレードオフを含めます。全体は約 `500 tokens` とし、不要な質問は追加しません。4 個以上ある場合は重要な 3 個を先に尋ね、回答後に残りを再評価します。
3. **Change Brief を提示する。** Change Brief は約 `800 tokens` とし、目的、対象範囲、明確な非目標、3 から 5 個の観測可能な受け入れシナリオ、重大なリスク、予定する検証を含めます。重要事項を省略せず簡潔にできない場合、AI は Full を推奨します。
4. **一度だけ承認を得る。** Lite の正式な承認点はちょうど 1 つです。完全な Change Brief を明示的に承認してから本番変更を始めます。Lite はワークフロー成果物ファイルを作成も更新もしません。Change Brief、進捗、Review はこの会話内だけに存在します。
5. **承認済み範囲を直接実装する。** Lite はテストを追加も変更もしません。`Red`、`Green`、`Refactor` を使わず、TDD と同等の信頼性も主張しません。重要な新しい動作や範囲拡大が必要になった場合、続行前に利用者へ戻ります。
6. **最低限の検証を行う。** 最終的なファイル範囲と差分を確認し、適用できる構文、lint、型チェック、build、設定、schema などの静的チェックを実行します。さらに既存の焦点を絞ったテストまたは手動 smoke check で、一つの主要な成功経路と一つの最も重要な失敗または境界経路を確認します。適用できる確認が失敗した場合は修正後に再実行し、実行できない確認は開示します。既知の未解決エラーがあれば無条件に完了とは言えません。
7. **簡潔な Review を行う。** 同じ AI が Change Brief の充足、差分範囲、失敗経路とセキュリティ、検証不足、残存リスクを確認します。対応可能な findings は一つのまとまりで提示し、修正前に承認を得てから、関連する検証を再実行します。承認されなかった項目は変更せず、未解決として報告します。対応可能な findings が 0 件の場合、AI はそのことを明示し、空の修正承認点を作りません。
8. **完了を報告する。** 完了報告は通常約 `500 tokens` とし、提供した動作、変更領域、観測した検証と結果、実行できない確認、未解決 findings、残存リスクを示します。失敗、阻害要因、セキュリティ上の懸念、不足または利用できない根拠、未解決 findings がある場合は目標を超えてもよく、短縮のために隠してはいけません。

## 高リスクの操作

認証と認可、支払い、データ移行、破壊的なデータ操作、公開契約、複数モジュールの構造、並行または非同期処理、外部への副作用では、Full の強い追跡可能性が必要になる場合があります。

Lite が実装前にその証拠を見つけた場合、リスクを説明し、現在の操作だけを Full に切り替えるか尋ねます。リスクを受け入れて Lite を続けることもできます。この選択は Config に書き込まれず、他のセッションでは引き続き Config が基準です。

重大なリスクが実装中に判明した場合、AI はそれ以上の変更を止めて再度確認します。Full へ切り替える場合は現在観測できる変更を保持し、まだ満たしていない最初の Full 承認点へ戻ってから続けます。モードの回答がない間、作業は停止します。

## Codex で始める

Plugin をインストールした後、新しい Codex タスクで次のように入力します。

```text
$ask-then-do-it 作りたいものは……
```

モードを明示しない場合、AI は Config から Full または Lite を選びます。承認済みの Full `direct` Ticket は `$implement-direct` へ進み、Lite は上記の単一 Change Brief フローに従います。

## Gemini またはその他の AI で始める

新しい会話ごとに `generic-workflow.md` を貼り付けてから、要望を説明します。Generic workflow は実際に利用できるツールの範囲でのみ動作し、会話だけのホストはファイル編集や検証を実行したと主張できません。

## 新しいセッションを始めるとき

新しいセッションではモードを再判定し、前回の操作だけの選択を再利用しません。Full は保存済み文書から再開できます。Lite の Change Brief、承認、進捗、Review にはセッションをまたぐ状態がないため、必要なら現在のプロジェクト状態から新しい brief を組み立てます。

## 最後の確認

- [ ] モードは現在の操作、プロジェクト Config、ユーザー Config、Full fallback の順序で決まった。
- [ ] Full では要件、仕様、Ticket 計画を承認し、すべての Ticket にテストを追加するか一度に回答した。
- [ ] Lite には承認済みの Change Brief が一つだけあり、新しいテストやフロー文書を作っていない。
- [ ] 観測した検証、実行できない確認、未解決 findings、残存リスクを開示した。
- [ ] 高リスク時の切り替えは現在の操作だけに影響し、別セッションの Config 動作を変えない。
