# Ask Then Do It Generic 使用ガイド

このガイドでは、Gemini など長い文章を受け取れる AI サービスで Ask Then Do It を使う方法を説明します。Generic 版では Plugin をインストールせず、ワークフローを会話に貼り付けます。

## ダウンロードと展開

[ask-then-do-it-generic-1.3.1.zip をダウンロード](https://github.com/Mysterio1001/Ask-Then-Do-It/releases/download/v1.3.1/ask-then-do-it-generic-1.3.1.zip)して展開します。

パッケージの主なファイルは次のとおりです。

- `START-HERE.ja.md`：簡単な使用方法。
- `generic-workflow.md`：通常使用する完全なワークフロー。
- `prompts/`：段階別の 11 個のモジュール。
- `LICENSE` と `THIRD_PARTY_NOTICES.md`：ライセンスと出典に関する情報。

## すぐに始める

新しい会話では毎回、次の手順で始めます。

1. `generic-workflow.md` を開きます。
2. 全文をコピーして、新しい AI の会話に貼り付けます。
3. 実現したいことと使用したい言語を伝えます。
4. 以前の Full 作業を続ける場合は、保存した Full の重要文書も貼り付けます。

例：

```text
予約サイトを作りたいです。
日本語で回答してください。
```

AI の最初の有効な返答ではワークフローモードを決定し、そのモードの質問と承認の規則に従います。別途「開始」と入力する必要はありません。

## ワークフローモードの設定

貼り付けたワークフローは、操作ごとに次の順序でモードを決定します。

1. 「今回は Full」「今回は Lite」など、現在の操作に対する明示的な指示。
2. ワークフロー内のデフォルトモード宣言。
3. Full fallback。

`generic-workflow.md` の先頭付近にある一つの宣言を、次のいずれかの行にします。

- `Default workflow mode: full`
- `Default workflow mode: lite`

宣言がないか未対応の値なら Full を使います。明示的な上書きは現在の操作だけに影響し、宣言を変更しません。新しいセッションでは、別の明示指示がない限り、その会話へ貼り付けた宣言から始めます。Generic は Codex Config を読み取りません。両モードの詳しい流れは [Full / Lite ワークフローガイド](getting-started-simple.ja.md)を参照してください。

Generic はホストの能力を正直に扱います。AI に会話だけの能力しかない場合、repository の確認、ファイル編集、コマンドやテストの実行、状態の永続化、観測済み検証の報告、独立 Review はできません。追加ツールがあるサービスでも、実際に提供される能力の範囲だけで操作します。

## Full モードの承認点

Full モードでは、AI は一度に一つの要件質問だけを行います。最初の要件質問とそれ以降の各質問には、推奨回答と主なトレードオフを添えます。Full には 3 つの承認点があります。

1. 要件が明確になったとき。
2. 仕様が期待する結果を正しく表しているとき。
3. Ticket 計画を実行できる状態になったとき。

3 回目の承認前に、AI はまずすべての Tickets を示し、各 Ticket のテスト方針を提案します。Ticket ごとに、テストを追加すると作業時間が増える可能性があり、追加しないと確認の信頼度が下がることを説明します。すべての Ticket についてテストを追加するかどうかを一度に回答でき、全部に追加、全部に追加しない、または一部だけを指定できます。既定値はありません。一部だけを指定して残りを説明しなかった場合、AI は未決定の Tickets だけを確認します。

承認後、テストを追加する Ticket は内部で `tdd` と記録されて TDD モジュールに進みます。テストを追加しない Ticket は `direct` と記録されて `direct-implementation.md` に進みます。direct のガイダンスは振る舞いテストを作成も実行もせず、Review は `tests: skipped-by-user` を保持します。3 回目の承認後に実装段階へ進みます。変更を依頼した場合、AI は現在の段階にとどまり、内容を修正します。

## Lite モードの質問と承認

提示された根拠ですべての阻害要因を解消できる場合、Lite は質問が不要な場合があります。それ以外では、各回最大 3 つの阻害要因に関する質問を行います。その後、1 つの Change Brief を提示し、実装前に 1 回の承認を待ちます。

## できることの範囲

Generic 版は会話の中でワークフローを案内します。それ自体がファイルを直接編集したりテストを実行したりすることはできません。提案、文書、実装内容を提示できますが、実際のファイル操作は利用する AI サービスのツール機能によって異なります。

Review も、会話に貼り付けたコード、文書、テスト結果だけを対象にします。情報が不足している場合、AI は現在確認できないことを明確に示します。

## 進捗を保存する

新しい会話では、以前の内容が記憶されていないことがあります。作業の継続方法はモードによって異なります。

### Full

Full は永続化できるワークフロー文書を作成します。Full の段階で重要文書が作成されたら保存してください。たとえば次のものです。

- 要件記録。
- Project Knowledge Base。
- 仕様。
- 各 Ticket にテストを追加するかと、内部経路を含む Ticket 計画。
- Review またはアーキテクチャ改善レポート。

新しい会話で Full を続けるときは：

1. `generic-workflow.md` をもう一度貼り付けます。
2. 保存した文書を全文貼り付けます。
3. 続けたい内容や変更したい内容を伝えます。

AI は提示された内容を確認し、最初の未完了の Full 段階へ進みます。

### Lite

新しい Lite セッションでは、現在の指示とその会話に貼り付けた宣言からワークフローモードを再決定します。Lite の Change Brief、承認、進捗、Review は永続化されないため、その未保存状態を再開できません。AI は利用可能な repository の状態とユーザー入力から新しい Change Brief を再構築します。

## 11 個の詳細モジュール

通常は `generic-workflow.md` を使用します。流れに慣れたら、`prompts/` 内の特定のモジュールを直接貼り付けられます。

Generic が常に Lite になるわけではありません。モジュールの貼り付けで選択されるのは段階であり、ワークフローモードではありません。既存のモード優先順位と結果は変わりません。`bootstrap.md` と `orchestration.md` が完全なモード判定を担います。

他の 9 個の単独で貼り付けられるモジュールは、判定器なしで貼り付けられる可能性があるためだけに、同じ限定的で最小限の直接入口ガードを備えます。これは完全なモード判定の所有権を移すものではありません。構成済み orchestration によって証明済みのモードは再利用します。モードが未証明の直接貼り付けに限り、`現在の操作に対する明示的な指示 > 利用可能な埋め込み宣言 > Full fallback` を適用します。指示が競合すると停止して確認を求めます。無効な宣言では Full を選択します。結果を永続化しません。Lite と判定済みなら `lite-workflow.md` へ進みます。Full と判定済みの状態で `lite-workflow.md` に直接入ると `orchestration.md` へ戻ります。

| Prompt | 用途 |
| --- | --- |
| `bootstrap.md` | 現在の進捗と次の段階を判断する |
| `orchestration.md` | ワークフロー全体を調整する |
| `lite-workflow.md` | モード決定後に Lite の全ライフサイクルを案内する |
| `requirements.md` | 要件について一度に一つ質問する |
| `documented-requirements.md` | 要件を確認し、長期的なプロジェクト知識を整理する |
| `specification.md` | 承認済みの要件を仕様にまとめる |
| `ticket-planning.md` | 仕様を縦割りの Tickets に分け、テストを追加するかを一度に確認する |
| `direct-implementation.md` | 振る舞いテストなしの直接実装ガイダンスを提示する |
| `tdd-implementation.md` | Ticket ごとにテストと実装を準備する |
| `review.md` | 会話で提示された内容を Review する |
| `architecture-improvement.md` | アーキテクチャ上の問題と改善案を分析する |
