# Ask Then Do It：モデルに依存しない AI 開発フローの設計

Ask Then Do It は「実行前に確認する」という考え方を、`Full` と `Lite` の 2 つの上位モードに分けます。Full は意思決定、実装、Review の完全な根拠を残します。Lite は範囲が明確でリスクの低い作業についてフローの材料を減らしながら、利用者の権限、最低限の検証、正直な報告を維持します。

上位の Full/Lite と、Full の Ticket 内部でのテスト選択は別の概念です。Lite は `direct` の別名ではなく、実装を許可するために架空の Full 文書を作ってはいけません。

## 解決する問題

一つの重いフローは追跡しやすい一方、小さな変更でも要件、仕様、Tickets、引き継ぎ材料を繰り返し生成して読み込みます。TDD だけを外しても、残りのフローコストは減りません。

そのため設計では、次の 2 つを同時に守ります。

- Full の既存の承認、文書、テスト選択、Review、アーキテクチャ改善の動作を変更しない。
- Lite はワークフローが制御する材料を減らし、検証信頼度と追跡可能性が低いことを開示する。

## Core と host の責任

Core はプロバイダー中立の Full/Lite 契約を所有します。対象はモード名、Full fallback、Full 互換性、Lite のライフサイクル、リスク時の停止、承認権限、最低検証、Review 修正権限、session の動作です。

| 層 | 責任 | 主張してはいけない能力 |
| --- | --- | --- |
| Core | 両モードに共通するモデル中立の意味と安全境界を定義する | host 固有の Config パスやツール能力を決めない |
| Codex Plugin | Codex adapter がユーザーとプロジェクトの Config、Skills、ファイル、コマンドを Core へ対応付ける | Core の意味を変更したり、一時的な操作選択を保存したりしない |
| Generic workflow | Generic adapter がデフォルトモード宣言と会話モジュールを Core へ対応付ける | ツールの根拠がなければ、ファイル編集、コマンド実行、観測したテスト結果を主張しない |

Codex adapter は Plugin の Config を読み、優先順位を解決し、実際の権限内でファイルとコマンドを操作します。Generic adapter はデフォルトモード宣言を持つ長文ワークフローを構成し、会話専用 host の能力を正直に扱います。

文書にも明確な ownership があります。3 言語の初心者ガイドが完全な Full/Lite 利用フローの基準であり、Codex と Generic のガイドは host 設定を担当します。短い入口ページは案内だけを行い、この設計ガイドは保守契約と token-proxy 目標を担当します。

## Adapter の同等性

host のツールが同じである必要はありませんが、同じ利用者の決定は同等の観測可能な結果を生む必要があります。同等性には少なくとも次を含みます。

- 現在の操作への明示的な指示は永続的なデフォルトより優先され、有効なデフォルトがなければ Full になる。
- Full は 3 つの承認を維持し、Lite は Change Brief の 1 承認だけを持つ。
- 高リスク切り替えは現在の操作だけに影響し、実装中に重大なリスクが判明しても再決定のため作業を停止する。
- Lite はフロー文書もテストも作らず、観測できた検証と利用できない検証の両方を開示する。
- Lite Review は findings を一括提示し、修正前に利用者の承認を得る。
- 新しい session はモードを再決定し、保存されていない Lite 状態の再開を主張しない。

Codex は直接編集と検証ができます。会話だけの Generic host は計画の提示や利用者提供の根拠を分析できますが、ツールの結果を主張できません。これは能力の違いであり、フローの結果や承認権限の違いではありません。

## Full の契約

Full は高リスク、複数モジュール、未確定の要件、監査が必要な作業向けです。既存のライフサイクルを変更しません。

1. repository reconnaissance を行い、要件の合意まで要件の質問を一度に一つ行う。
2. 要件の承認後にだけ、承認済み情報を Project Knowledge Base へ同期する。
3. 動作と失敗時の扱いを定義する仕様を作成し、承認する。
4. 縦割りの Tickets に分け、各 Ticket のテスト方針を提案する。その後、すべての Ticket でテストを追加するかどうかを一度に回答し、完全な計画を承認する。
5. Full はテスト選択を内部で `tdd` または `direct` に対応させます。TDD は Red、Green、Refactor を必要とし、direct は振る舞いテストを実行せず未テスト動作を記録します。
6. 実装根拠を保存し、独立した Review で 12 の視点から確認します。システム全体の問題はアーキテクチャ改善として分析し、新しい実装権限を得るため仕様と Tickets へ戻します。

要件の合意、仕様、Ticket 計画が Full の 3 つの正式な承認点です。モード resolver を Full の前に置くことはできますが、これらの契約を削除も短縮もできません。

## Lite の契約と低い追跡可能性

Lite の追跡可能性は Full より低くなります。Change Brief、承認、進捗、Review が現在の会話だけに残り、別の session が再開できるフロー文書にならないためです。このトレードオフは文書と完了報告で明確にします。

共通の Lite ライフサイクルは、対象を絞った reconnaissance とリスク評価、1 回につき最大 3 個の阻害質問、約 800 tokens の Change Brief、1 回の承認、直接実装、静的検証と成功・失敗経路の検証、簡潔な Review、findings 修正の承認、通常約 500 tokens の完了報告です。

Lite は振る舞いテストを追加も変更もせず、TDD を行いません。Full の 12 視点 Review や独立 reviewer も必須ではありません。それでも範囲拡大を止め、利用者の変更を保護し、利用可能な最低検証を行い、既知の失敗があれば無条件な完了主張を防ぎます。

## リスクと権限の境界

認証、権限、支払い、データ移行、破壊的なデータ操作、公開契約、複数モジュール構造、並行処理、非同期処理、外部への副作用は Lite 承認前に評価します。重大なリスクがあれば host は根拠を示し、現在の操作だけを Full に切り替えるか確認します。利用者はリスクを受け入れて Lite を続けることもできます。

実装中に新しいリスクが見つかった場合、それ以上の変更を停止します。Full へ切り替えるときは観測可能な変更を保ち、まだ満たしていない最初の Full gate へ戻ります。この選択で Config を書き換えたり、別 session に影響させたりしてはいけません。

## 再現可能な token proxy

release gate は Full と Lite を同等の代表シナリオで比較します。Fixture はタスク、決定、リスク、完成結果を同じに固定し、両モードに同じ正規化と計数方法を使います。これにより repository 内で失敗を再現できます。

計数にはワークフローが制御する材料を含めます。対象は質問、Change Brief または Full の文書、段階の指示、構成済み prompt の内容、繰り返される引き継ぎ、完了報告です。両モードへ同じ規則を適用し、Lite に不利な内容だけを特別に除外しません。

タスク固有のソースコード、必要なツール出力、非公開のモデル推論は、フローが決定的に制御できる共通コストではないため除外します。Fixture、計数規則、Full と Lite の生の計数、式をテストまたは release evidence で開示します。

削減率は `(Full proxy - Lite proxy) / Full proxy * 100` で計算します。代表シナリオで Lite が制御対象 proxy を 60% 以上削減できなければ、release gate は失敗します。

この proxy は repository が制御するフロー材料だけを検証します。API 請求額を保証するものではありません。総 context、非公開の推論コスト、cache 割引も保証せず、gate 通過を料金保証として説明してはいけません。

## 保守ルール

- Core のモード意味を変更するときは、Codex と Generic の対応も更新し、同等性の根拠を示す。
- Lite の追加によって、Full の一度に一つの質問、3 承認、Ticket ごとのテスト選択、TDD/direct の根拠、Review を弱めない。
- Lite の質問、Change Brief、完了報告の予算は利用者に見える出力の概算であり、失敗、リスク、不足する根拠を隠す理由にしない。
- 初心者ガイドは完全な利用フロー、host ガイドは設定を担当する。短い入口ページに完全なフローを複製せず、Lite 専用ガイドも追加しない。
- Generic workflow は実際の host 能力だけを主張し、ツールがなければ明確な handoff または未検証の説明を行う。
- 60% proxy は同等のシナリオと固定規則を使い、fixture や算法を変えるときは両モードを一緒に評価する。
